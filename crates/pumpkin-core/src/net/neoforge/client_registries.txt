# What a real 26.3 client expects in the registries the handshake synchronises.
#
# Generated from the client jar; nothing here is hand written and nothing may be edited by hand. A
# registry's ids are the positions of its entries, so a missing or moved entry renumbers every
# entry after it, and no error is reported anywhere -- the entries below are the oracle the sync is
# checked against (`the_synced_datapack_registries_are_the_clients` and
# `the_vanilla_entries_of_the_builtin_registries_are_the_clients` in `registries.rs`).
#
# Regeneration, against `libraries/com/mojang/minecraft/26.3/minecraft-26.3-client.jar`:
#
#   1. `datapack`: for each key of `pumpkin_data::registry::Registry::get_synced`, list the file
#      names under `data/minecraft/<key>/` in the jar, relative to that directory with `.json`
#      stripped -- that relative path is the entry's path, so the id is `minecraft:<path>`.
#
#   2. `builtin`: the entries of `BuiltInRegistries.<registry>` *in id order* (`getId`), dumped by
#      a throwaway program run on the client's own classpath -- the jar is the oracle for the
#      order too, and `entrySet` alone is not ordered:
#
#        net.minecraft.SharedConstants.tryDetectVersion();
#        net.minecraft.server.Bootstrap.bootStrap();
#        Registry<?> r = BuiltInRegistries.REGISTRY.getValue(Identifier.parse(key));
#        List<Identifier> names = ...;  // every `e.getKey().identifier()` of r.entrySet()
#        names.sort(comparingInt(n -> r.getId(r.getValue(n))));
#
# Format: `#` comments, `datapack`/`builtin` section markers, then `<registry>\t<entry>` lines.
# Entries are full ids in the order the client has them (`builtin` is positional; `datapack` is
# sorted, because a data pack registry's ids come from the order the server sends them in).
